CMPUT 350 - Project 2: ECS Engine and Platformer
================================================

Team members: Sarang Kim, Zifan Li


1. OVERVIEW
-----------

This project implements an Entity Component System (ECS) game engine in C++20 using SFML 3, together with a small platformer game built on top of the engine.

The project is divided into two main parts:
  - engine/: ECS infrastructure, entities, components, systems, and resource managers.
  - platformer/: game initialization and the platformer game setup.

The engine uses entities as identifiers, components to store game data, and systems to process entities with the required components. The engine also provides resource managers for sounds, sprites, the rendering window, and entities.

The platformer is designed around a player who can move, jump, wall-jump, and dash through a level while collecting stars. The game uses a camera that follows the player horizontally, a score display, and a spawner that creates moving stars.


2. WHAT IS IMPLEMENTED
----------------------

One entry per major part of the project: what exists, which files, and how it works.

[M1] Sound Manager
  - Implemented the SoundManager resource manager in engine/SoundManager.h and SoundManager.cpp.
  - Sounds are registered using a file path and a name, allowing the game to retrieve sounds by name instead of loading them directly wherever they are needed.
  - The manager owns the sound resources and provides access through GetSound.
  - This keeps sound loading and storage separate from the game systems that use the sounds.

[M2] Sprite Manager
  - Implemented the SpriteManager resource manager in engine/SpriteManager.h and SpriteManager.cpp.
  - RegisterTexture loads a texture and creates a sprite using the requested source rectangle.
  - Textures are stored in an unordered_map so that sprites can continue to refer to textures owned by the manager.
  - Sprites are stored in a vector, and SpriteID is used as an index to retrieve a registered sprite.
  - GetSprite provides access to a sprite using its SpriteID.
  - This allows game entities to refer to registered sprites without loading and managing textures themselves.

[M3] Window Manager
  - Implemented the WindowManager resource manager in engine/WindowManager.h and WindowManager.cpp.
  - The manager owns the SFML render window and provides access to it through GetWindow.
  - It also manages the relationship between world coordinates and window coordinates.
  - The camera can be configured through the world center and world scale.
  - Conversion functions allow systems to transform points and rectangles between world space and screen space.
  - This keeps camera and coordinate conversion logic out of individual game systems.

[M4] Camera Components and Camera System
  - Camera-related components are defined in CameraComponent.h, CameraFollowerComponent.h, and CameraShakeComponent.h.
  - CameraComponent stores the camera position, world-units-per-pixel scale, hard and soft exclusion rectangles, and camera tracking speed.
  - CameraFollower stores the entity ID of the entity that the camera should follow.
  - CameraShake stores the remaining shake frames and the offset used to determine the shake magnitude.
  - CameraSystem finds the camera and its follower, then adjusts the camera's horizontal position based on the follower's screen position.
  - The camera uses hard and soft follow boundaries. Crossing a hard boundary moves the camera directly, while crossing a soft boundary allows it to track smoothly.
  - The camera's vertical position remains fixed.
  - CameraSystem updates WindowManager with the resulting camera position and scale.

[M5] Sprite Component and Sprite System
  - SpriteComponent is defined in SpriteComponent.h.
  - It stores the SpriteID, the bounds of the sprite relative to the entity's location, and whether the sprite is drawn in world space or screen space.
  - SpriteSystem iterates through entities with SpriteComponent and draws their sprites using SpriteManager.
  - If an entity has a LocationComponent, its location is used as the base position for the sprite.
  - World-space sprites are converted to window coordinates through WindowManager.
  - The system uses a local copy of the registered sprite when applying position and scale, so drawing transformations do not modify the sprite stored in SpriteManager.
  - The window is displayed after the sprites have been drawn.

[M6] Score Component and Score System
  - ScoreComponent is defined in ScoreComponent.h.
  - It stores the current score, the entity IDs used to display the score, and the SpriteIDs corresponding to the digits 0 through 9.
  - ScoreSystem converts the score into three digits and updates the texture IDs of the corresponding digit entities.
  - The score display uses numeric sprites rather than text rendering.

[M7] Spawn Component and Spawn System
  - SpawnComponent is defined in SpawnComponent.h.
  - It stores the entity associated with the spawner, the type of entity to create, the sprite texture ID, the time until the next spawn, the interval between spawns, and the total number of spawning events.
  - SpawnSystem finds entities with SpawnComponent and counts down their spawn timers.
  - When a spawn is due, it creates a new entity at the spawner's location.
  - The spawned entity receives location, sprite, movement, and collision components.
  - Its movement direction and speed are randomized.
  - Spawner IDs are collected before creating new entities so that creating entities does not invalidate the entity iteration.

[M8] ECS Engine and System Integration
  - The engine provides an EngineView interface through which systems access the resource managers and EntityManager.
  - Systems are registered through SystemManager and run consecutively in their registration order.
  - The engine's component pack includes the components required by the platformer, including location, movement, collision, sprite, spawn, camera, camera follower, input, gravity, camera shake, score, and respawn components.
  - The platformer main file registers the systems used by the game, including input, gravity, movement, collision, score, camera, sprite, and spawn systems.

[M9] Entity Manager
  - Implemented in engine/EntityManager.h, with tests in engine/EngineTest.cpp.
  - Entities live in a vector. An EntityID is its position. IDs are never reused: a removed entity stays as an invalid gap (mValid is false).
  - mSlots is a table with one row per entity and one column per component type. A cell holds the position of that entity's component in the type's storage, or kNullComponent.
  - Each component type has a ComponentStorage (values, valid flags and a free list). RemoveComponent puts the slot on the free list; AddComponent reuses a free slot before growing the vector.

[M10] Engine main loop, events, frame time and debug drawing
  - Implemented in engine/ECSEngine.h: ProcessEvents, Run, GetFrameTime and DebugDraw.
  - ProcessEvents polls SFML events. A close event returns false. A key press or release sets or clears the key's bit in keydown of every InputComponent. The D key toggles debug drawing.
  - Run limits the window to 60 frames per second, then loops while ProcessEvents returns true. Each frame it measures the frame time, runs the systems through SystemManager, draws the collision boxes if debug is on, and shows the frame once with display(). It stops if a system returns kExit.
  - Frame time is in seconds (Lecture 15: velocity in pixels per second, applied "given frame timing"). EngineView has a pure virtual GetFrameTime(), and ECSEngine returns mFrameTime. The clock is restarted once before the loop so loading time is not counted in frame 1. A frame is capped at 1/30 s, so a slow frame cannot move an entity through the floor.
  - DebugDraw outlines every collision box, red for static entities and green for moving ones, with WindowManager::DebugFrameRect.

[M11] Collision Component, Collision Late System and Collision System
  - CollisionComponent (engine/CollisionComponent.h): all six flags default to 0 and both Rects to {}, so a new component never holds leftover memory.
  - CollisionLateSystem (engine/CollisionLateSystem.h) stores each entity's collision box at its world position in previousCollisionBox before the entity moves.
  - CollisionSystem (engine/CollisionSystem.h): Overlaps(a, b) returns false when a is entirely left of, right of, above or below b. Boxes that only touch along an edge do not overlap.
  - For every moving entity it clears the four contact flags, then checks it against every other entity (static ones too). On an overlap, previousCollisionBox decides which side was hit (top, bottom, left or right). The entity is pushed out on that side, the matching flag is set, and its velocity on that axis is set to 0.
  - After each push the entity's box is rebuilt from the new location, so a second tile in the same frame (for example where two wall tiles meet) is tested against the new position, not the old one.
  - Player hitting a star: the star is removed, the score goes up by 1 and the "star" sound plays.
  - Star hitting a static obstacle: it bounces, keeping 70% of its speed (kBounceKeep).
  - A hit faster than kShakeMinSpeed sets the player's CameraShake, along the hit's axis. Landing plays the "land" sound.
  - Player touching a spike (a tile with doesDamage set; 'x' in world.map): the player goes back to its RespawnComponent location with zero velocity.

[M12] Movement System and Gravity System
  - MovementSystem (engine/MovementSystem.h) adds velocity * frame time to the location of every entity with a MovementComponent and a LocationComponent.
  - GravitySystem (engine/GravitySystem.h) adds acceleration * frame time to the velocity. Falling is faster than rising (kFallMultiplier 2.0), and holding Down while falling is faster again (kFastFallMultiplier 1.5).
  - Wall slide: falling while pressing into a wall caps the fall speed at kWallSlideSpeed and plays the "wall" sound.

[M13] Input System
  - Implemented in engine/InputSystem.h. It only changes velocity; MovementSystem moves the entity later in the frame.
  - Running: Left and Right add an acceleration each frame (smaller in the air), clamped to kMaxRunVelocity. With no arrow held the player stops.
  - Jump: a fresh Z press on the ground sets an upward velocity and plays the "jump" sound. A fresh press is "keydown now and not lastKeydown"; lastKeydown is copied from keydown at the end of each frame.
  - Variable jump height: letting go of Z caps the upward speed at kJumpCutVelocity, so a short press gives a short jump.
  - Wall jump: a fresh Z press while falling against a wall and holding into it pushes the player up and away from the wall.
  - Dash: a fresh C press, at most once per second (kDashInterval frames), sets a fast sideways velocity for kDashDuration frames. During a dash the run code is skipped and vertical velocity is 0, so the dash goes straight sideways. The dash goes the way the player last faced (InputComponent::facing, set by the last arrow held), even if no arrow is held when C is pressed.

[M14] Map loading and game setup
  - LoadMap (platformer/main.cpp) reads the map format: the dictionary (one letter per tile, with a texture rectangle and, for type 2 maps, a collision box), the "map origin tile size" line, and the grid. Each letter except '.' becomes an entity with a location, a sprite and, for type 2 maps, a static collision box. 'S' becomes the star spawner instead.
  - main() registers the four sounds ("jump", "land", "star", "wall"), loads sky.map then world.map (the sky is created first, so it is drawn first), and creates the player, the score digits, the camera and the extra star.
  - The extra star is at (3296, 640), in the gap between the second spike wall and the end wall. It can only be reached by going over the wall, which needs a wall jump.


3. DESIGN DECISIONS AND API CHANGES
-----------------------------------

[M1] Resource managers
  - SoundManager, SpriteManager, and WindowManager keep resource ownership separate from the systems that use those resources.
  - Systems access managers through EngineView rather than directly accessing the engine's private manager variables.
  - SoundManager uses names to retrieve registered sounds.
  - SpriteManager uses SpriteID values to retrieve registered sprites. Textures are stored separately from sprites so that sprites can refer to manager-owned textures.
  - WindowManager centralizes coordinate conversion and camera configuration so that systems do not need to implement their own world-to-screen transformations.

[M2] Sprite drawing
  - SpriteComponent stores the sprite's bounds relative to the entity's base location.
  - SpriteSystem adds the relative sprite offset to the entity's location before drawing.
  - World-space and screen-space sprites are handled differently because only world-space sprites need to be transformed by the camera.
  - A copy of the registered sprite is used for drawing so that position and scale changes do not persist in the manager's stored sprite.

[M3] Camera behavior
  - The camera follows the player horizontally while keeping its vertical position fixed.
  - The hard and soft exclusion rectangles define the screen-space regions used to determine when the camera should move.
  - Hard following prevents the player from reaching the outer screen boundaries, while soft following gradually recenters the player.
  - Camera shake is handled through CameraShake data so that collision handling can communicate shake information to CameraSystem without directly controlling the window.

[M4] Score display
  - The score is represented by three digit entities.
  - Each digit entity uses one of the ten registered numeric sprites.
  - ScoreSystem updates the sprite texture IDs rather than creating new text objects every frame.

[M5] Entity spawning
  - SpawnSystem collects the IDs of active spawners before creating entities. This avoids modifying the entity collection while iterating through it.
  - Spawned stars receive their own components and randomized movement.
  - Collision resolution and bouncing behavior are handled separately by the collision systems.

[M6] Resource lifetime and ownership
  - Resource managers own the resources they register.
  - A reference returned by GetSound or GetSprite does not transfer ownership to the caller.
  - GetWindow returns a shared pointer to the SFML window, allowing systems to access the window while the engine and WindowManager retain ownership.
  - EntityManager and the other managers are owned by the engine. Systems should access them through EngineView and should not retain references beyond the lifetime guaranteed by the manager.
  - References to sprites stored in SpriteManager should not be retained across later sprite registrations unless their validity is guaranteed by the implementation, since the sprites are stored in a vector.

[M7] Entity storage
  - Entity IDs are never reused, so an old EntityID can never silently point at a new entity; IsValid tells whether it still exists.
  - References from GetComponent and GetComponentStorage stay valid until the next AddComponent of the same type, because the storage vector can grow. This is documented in EntityManager.h.

[M8] Frame time (API change)
  - Added a pure virtual GetFrameTime() to EngineView, returning float seconds, implemented by ECSEngine. Speeds are therefore in pixels per second and gravity in pixels per second squared, so movement does not depend on frame rate.
  - Counts (dash cooldown, dash length, shake length) are in frames; the 60 fps limit in Run keeps them steady.

[M9] One display() per frame (API change)
  - display() was moved out of SpriteSystem into ECSEngine::Run, and SpriteSystem now calls clear() before drawing. The frame is shown once, after the debug boxes, so the boxes are drawn on top of the sprites.

[M10] System order
  - Order in main.cpp: CollisionLate, Input, Gravity, Movement, Collision, then the drawing and game systems.
  - CollisionLateSystem must run before MovementSystem so previousCollisionBox holds the position before the move.
  - InputSystem and GravitySystem read last frame's contact flags (onGround, onLeftWall, onRightWall), because CollisionSystem runs after them. One frame of delay is not noticeable.

[M11] Collision side detection
  - The side that was hit is decided from previousCollisionBox (where the entity was before it moved), not from the size of the overlap. An entity that was above the other box last frame has landed on it.
  - Static entities are never moved, but they still block others because they are visited in the inner loop.
  - A push is written as: location = target edge - box size (if needed) - collisionBox offset, because collisionBox is an offset from the location.

[M12] Wall slide as a cap
  - The wall slide caps the fall speed instead of using a smaller gravity, because a smaller gravity only slows the speed-up and a long slide would still get fast.


4. IMPLEMENTATION NOTES AND REMAINING WORK
------------------------------------------

  - The platformer entry point is platformer/main.cpp.
  - All the required systems are implemented and the game is playable: run, jump, variable jump height, wall slide, wall jump, dash, faster falling, star collection, score updates, bouncing stars, spikes that send the player back to the start, camera shake and the D debug toggle.
  - The project builds with no errors and no warnings with -Wall -Wextra -Wpedantic on Windows.
  - Known gaps:
      * There is no sweep test, so a very fast entity could pass through a thin box in one frame. The 1/30 s frame cap keeps steps small enough for this level.
      * disabledTimer is not used.
      * An unknown letter in a map silently gets sprite 0, because unordered_map [] inserts a default for a missing key.
      * The spawner values (first spawn after 60 frames, one every 120 frames, 1000 in total) are guesses. The tuning constants in InputSystem.h, GravitySystem.h and CollisionSystem.h were chosen by playtesting. The spec gives neither.
      * The camera exclusion rectangles are our reading of the comments in CameraComponent.h; the spec does not give the numbers.
  - world.map and sky.map are committed with git add -f, because *.map is in .gitignore.
